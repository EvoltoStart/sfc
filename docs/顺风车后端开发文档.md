# 顺风车后端开发文档

## 1. 文档目标

本文档用于指导顺风车项目后端开发，面向以下对象：

1. Go 后端开发
2. 数据库设计与迁移开发
3. 支付、地图、对象存储等第三方集成开发
4. 后台联调、测试和运维人员

本文档强调：

1. 模块边界
2. 核心数据结构
3. 状态机与规则
4. API 设计
5. 异步任务与审计
6. 一期可交付实现顺序

---

## 2. 后端建设目标

### 2.1 一期核心目标

后端一期只做两个闭环：

1. 真实顺风车业务闭环
2. 合规审计闭环

### 2.2 一期必须保证的能力

1. 微信登录与用户体系
2. 车主认证与车辆认证
3. 行程发布与匹配
4. 顺路度校验
5. 接单频次限制
6. 订单状态流转
7. 平台线上支付与退款
8. 钱包与结算
9. 行程轨迹留痕
10. 紧急联系人与 SOS
11. 后台审核、订单处理、风控查询、财务流水

### 2.3 一期不建议深做的能力

1. 全链路录音处理
2. 跨平台订单同步
3. 复杂补贴体系
4. 资源占用费自动扣减
5. 高级推荐算法

## 3. 架构选择

### 3.1 一期架构建议

一期采用模块化单体，不直接上微服务。

原因：

1. 复杂度主要来自业务规则，不是超大流量
2. 订单、支付、结算、风控、轨迹高度耦合
3. 当前更需要快速交付与稳定联调

### 3.2 架构分层

建议按四层组织：

1. 接口层：HTTP Handler、鉴权、中间件
2. 应用层：UseCase、事务编排、幂等控制
3. 领域层：实体、仓储接口、领域服务、规则服务
4. 基础设施层：MySQL、Redis、MQ、对象存储、地图 SDK、支付 SDK

## 4. 模块拆分

## 4.1 auth 模块

负责：

1. 微信登录
2. Token 签发
3. 登录态校验
4. 角色识别

关键点：

1. 支持小程序登录换取 session
2. Token 中写入用户 ID、角色、会话版本
3. 封禁用户登录拦截

## 4.2 user 模块

负责：

1. 用户基础资料
2. 实名认证状态
3. 紧急联系人
4. 用户状态管理

关键点：

1. 用户表与实名认证表分离
2. 紧急联系人必须支持默认联系人
3. 用户封禁后前端要拿到明确错误码

## 4.3 vehicle 模块

负责：

1. 车辆管理
2. 驾驶证认证
3. 车辆审核
4. 默认车辆设置

关键点：

1. 驾驶证和车辆认证流程独立
2. 默认车辆唯一
3. 车主未完成认证时禁止发布行程

## 4.4 trip 模块

负责：

1. 行程发布
2. 行程编辑
3. 行程取消
4. 我的行程查询
5. 常用路线管理

关键点：

1. 行程发布前要做价格预览、顺路度校验、频控校验
2. 已有订单的行程禁止直接编辑核心字段
3. 行程状态与订单状态联动

## 4.5 matching 模块

负责：

1. 乘客搜索匹配
2. 顺路度计算
3. 候选排序
4. 频控规则校验
5. 规则快照生成

关键点：

1. 顺路度大于等于 90% 才进入结果集
2. 匹配排序优先级为顺路度、时间匹配、评分、距离偏差
3. 每次计算要持久化快照

## 4.6 order 模块

负责：

1. 申请同行
2. 接受/拒绝
3. 订单创建
4. 订单状态机流转
5. 取消、异常处理
6. 上下车确认

关键点：

1. 一个乘客对同一行程的有效申请需要唯一约束
2. 接受申请后才能生成正式待支付订单
3. 上车、到达操作只允许乘客端触发

## 4.7 payment 模块

负责：

1. 支付下单
2. 微信回调验签
3. 退款
4. 平台服务费记录
5. 结算触发

关键点：

1. 支付单与业务订单分离
2. 回调必须幂等
3. 退款必须关联原支付单

## 4.8 wallet 模块

负责：

1. 钱包账户
2. 账单流水
3. 结算入账
4. 提现申请

关键点：

1. 钱包流水必须采用记账方式，不直接改余额不留流水
2. 结算与提现走独立流水类型

## 4.9 safety 模块

负责：

1. 紧急联系人设置
2. 行程分享
3. SOS 事件
4. 轨迹点采集
5. 风险事件记录
6. 导出审计

关键点：

1. 轨迹点与轨迹汇总分表
2. SOS 事件要支持处理状态
3. 导出轨迹和录音元数据必须留操作日志

## 4.10 admin-auth 模块

负责：

1. 后台账号登录
2. 后台会话校验
3. 角色权限加载
4. 菜单与按钮权限判断
5. 后台账号停用控制

关键点：

1. 后台认证与小程序用户认证分离，避免复用用户 token
2. 权限校验至少覆盖路由权限和按钮权限
3. 后台权限变更后需要支持会话内刷新或重新拉取

## 4.11 ops 模块

负责：

1. 资质审核
2. 工单处理
3. 投诉处理
4. 异常订单处理
5. 专线司机管理

## 4.12 cms/report 模块

负责：

1. 轮播图
2. 用户协议
3. 隐私政策
4. 安全须知
5. 帮助中心
6. 报表统计

## 5. 核心状态机

## 5.1 行程状态

1. `DRAFT`：草稿
2. `PUBLISHED`：已发布待匹配
3. `MATCHING`：匹配中
4. `CONFIRMED`：已确认
5. `IN_PROGRESS`：进行中
6. `COMPLETED`：已完成
7. `CANCELLED`：已取消

### 行程状态流转规则

1. 发布成功后从 `DRAFT` 到 `PUBLISHED`
2. 存在有效申请后进入 `MATCHING`
3. 存在已支付订单后进入 `CONFIRMED`
4. 乘客确认上车后进入 `IN_PROGRESS`
5. 乘客确认到达后进入 `COMPLETED`
6. 无履约前取消进入 `CANCELLED`

## 5.2 申请状态

1. `PENDING_DRIVER_CONFIRM`
2. `ACCEPTED`
3. `REJECTED`
4. `CANCELLED`
5. `EXPIRED`

### 关键流转

1. 乘客发起同行申请后进入 `PENDING_DRIVER_CONFIRM`
2. 车主接受申请后，申请状态变更为 `ACCEPTED`
3. 车主拒绝后进入 `REJECTED`
4. 乘客主动撤销申请后进入 `CANCELLED`
5. 超过有效时间未处理的申请进入 `EXPIRED`

## 5.3 订单状态

1. `PENDING_PASSENGER_PAY`
2. `PENDING_DEPART`
3. `IN_PROGRESS`
4. `PENDING_ARRIVAL_CONFIRM`
5. `COMPLETED`
6. `CANCELLED`
7. `EXCEPTION_HANDLING`
8. `REFUNDED`

### 关键流转

1. 只有车主接受申请后才创建正式订单
2. 新建订单默认进入 `PENDING_PASSENGER_PAY`
3. 支付成功后进入 `PENDING_DEPART`
4. 乘客确认上车后进入 `IN_PROGRESS`
5. 到达确认后进入 `COMPLETED`
6. 支付后取消需进入退款链路

## 5.4 审核状态

1. `PENDING`
2. `REVIEWING`
3. `APPROVED`
4. `REJECTED`

## 5.5 支付状态

1. `INIT`
2. `PAYING`
3. `PAID`
4. `FAIL`
5. `REFUNDING`
6. `REFUNDED`

## 6. 核心规则设计

## 6.1 顺路度规则

### 目标

保证平台业务属于顺风车撮合，而不是网约车派单。

### 一期规则

1. 乘客与车主路线的顺路度必须大于等于 90%
2. 搜索结果只展示满足阈值的候选
3. 行程发布时要保留校验记录
4. 匹配时要重新计算一次

### 快照字段

1. 规则版本
2. 乘客起终点坐标
3. 车主起终点坐标
4. 途经点
5. 规划距离
6. 偏移距离
7. 顺路度结果
8. 是否通过

## 6.2 接单频控规则

### 默认规则

1. 市内每日 4 单
2. 跨城每日 2 单
3. 月累计 60 单

### 设计要求

1. 配置化，不写死
2. 每次校验产生日志
3. 支持城市维度扩展
4. 超限后禁止发布或禁止继续接单

## 6.3 定价规则

### 一期费用构成

1. 里程费
2. 高速费
3. 平台服务费

### 一期规则

1. 平台服务费默认按车费 8%
2. 费用明细独立入库
3. 定价计算产生审计日志

## 6.4 取消与退款规则

### 一期建议

1. 未支付取消：直接关闭
2. 支付后未上车取消：按规则退款
3. 上车后取消：进入异常处理
4. 所有退款都走原路退回

## 6.5 安全规则

1. 轨迹点按时间间隔与关键节点同时采集
2. SOS 触发后必须入库并推送后台
3. 轨迹导出、录音调取都要留痕

## 8. API 设计

## 8.1 统一规范

### 路径规范

1. 公共接口前缀：`/api/v1`
2. 后台接口前缀：`/api/v1/admin`

### 返回规范

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "requestId": "trace-id"
}
```

### 错误码建议

1. `USER_NOT_LOGIN`
2. `USER_FORBIDDEN`
3. `DRIVER_NOT_VERIFIED`
4. `ROUTE_SCORE_NOT_PASS`
5. `FREQUENCY_LIMIT_EXCEEDED`

## 9. 事务与幂等设计

## 9.1 必须使用事务的场景

1. 接受申请并创建订单
2. 支付成功回调并更新订单状态
3. 到达确认并触发结算
4. 退款成功并回写订单状态
5. 提现申请创建与余额冻结

## 9.2 幂等要求

### 支付回调

必须基于：

1. `out_trade_no`
2. `pay_status`
3. 幂等日志

### 上下车确认

必须限制：

1. 只有乘客本人可操作
2. 同状态只允许确认一次

### SOS 上报

允许重复点击，但需要：

1. 生成唯一事件 ID
2. 防止同一秒重复写多条完全相同记录

## 16. 最终建议

后端开发不要一开始追求“模块数量多”，而要先追求“主链路和合规链路稳定”。

一期后端最核心的三个成功标准是：

1. 订单状态机稳定
2. 支付退款结算稳定
3. 顺路度、频控、轨迹留痕可追溯

只要这三件事做好，后续会员、专线、补贴、录音、跨平台扩展都会更顺。
