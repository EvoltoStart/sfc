# 顺风车 Agent 开发任务单

## 1. 文档目标

本文档用于把顺风车项目拆解成多个可并行执行的 Agent 任务单，目标是：

1. 明确每个 Agent 的边界
2. 降低并行开发时的冲突
3. 让每个 Agent 拿到任务后可以直接开工
4. 让负责人可以快速检查依赖关系和完成度

---

## 2. 总体分工原则

### 2.1 任务拆分原则

1. 每个 Agent 只拥有一个清晰责任域
2. 每个 Agent 必须有明确输入、输出、依赖和验收标准
3. 公共枚举、状态机、接口契约优先冻结，避免多 Agent 自行发明
4. 先主链路，后外围页；先规则稳定，后样式优化

### 2.2 统一约束

所有 Agent 必须遵守：

1. 不得新增未定义的订单状态
2. 不得在前端自行实现顺路度、频控、价格规则
3. 后端关键写操作必须留审计
4. 文档变更要同步回写到 `docs/`
5. 公共常量和 DTO 不得私自复制多份

---

## 3. 里程碑与执行顺序

### 3.1 里程碑划分

#### 里程碑 M1：骨架期

目标：

1. 前端壳搭建完成
2. 后端壳搭建完成
3. 数据库基础表确定
4. 登录与基础路由可跑通

#### 里程碑 M2：主链路期

目标：

1. 发布行程
2. 搜索匹配
3. 申请同行
4. 接受申请
5. 支付
6. 上下车确认
7. 自动结算

#### 里程碑 M3：合规后台期

目标：

1. 资质审核
2. 轨迹留痕
3. SOS
4. 风控后台
5. 财务流水

#### 里程碑 M4：上线准备期

目标：

1. 联调与回归
2. 部署脚本
3. 监控告警
4. 上线清单

### 3.2 推荐执行顺序

1. Agent A 冻结公共基线
2. Agent B、C、D、E 并行搭骨架
3. Agent F、G、H 并行做核心后端
4. Agent I 从第一周开始维护测试和联调
5. Agent J 在 M2 后半段切入部署与监控

## 15. 任务依赖关系

### 15.1 强依赖

1. Agent A 必须先输出冻结版基线
2. Agent C 必须先于 Agent D、E 输出小程序骨架
3. Agent G 的认证和行程能力是 Agent H 的前置
4. Agent H 的订单与支付能力是 Agent I 的前置
5. Agent K 的环境能力要在 M1 完成前具备

### 15.2 可并行任务

1. Agent B 与 Agent C 可并行
2. Agent D 与 Agent E 可并行
3. Agent F 与 Agent I 的后台接口联调可并行推进

## 17. DoD 完成定义

一个 Agent 的任务要算完成，至少必须满足：

1. 对应模块代码或文档已提交
2. 本 Agent 范围内自测完成
3. 关键异常场景已处理
4. 依赖方可以接入
5. 变更点已记录到文档

---

## 19. 负责人检查清单

负责人每天至少检查：

1. 状态枚举是否有新增冲突
2. 接口字段是否有变更未同步
3. 是否有人绕过公共组件或公共常量
4. 主链路 blocker 是否已暴露
5. 支付、顺路度、频控、轨迹这四条高风险链路是否按计划推进

---

## 20. 最终建议

多 Agent 并行开发最容易出问题的地方不是“写不出来”，而是“各写各的”。这个任务单的核心价值不是把人分开，而是把边界先分清。

建议实际执行时始终记住三条：

1. 公共基线先冻结
2. 主链路优先于外围功能
3. 任何跨 Agent 冲突，先回到接口清单和表结构文档解决
