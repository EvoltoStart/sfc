# 顺风车全流程开发部署文档

## 1. 文档目标

本文档用于指导顺风车项目从需求冻结、开发协作、测试联调到上线部署的完整流程，面向以下对象：

1. 项目经理
2. 前端开发
3. 后端开发
4. 测试工程师
5. 运维与部署人员
6. 负责人或交付经理

本文档解决以下问题：

1. 项目从 0 到 1 的开发顺序
2. 环境如何准备
3. 代码如何协作与提测
4. 前后端如何联调
5. 系统如何部署、监控、回滚

---

## 2. 项目交付目标

### 2.1 一期上线目标

一期只上线最小闭环：

1. 车主发布行程
2. 乘客搜索匹配
3. 发起同行申请
4. 车主接受申请
5. 平台支付
6. 确认上车
7. 确认到达
8. 自动结算
9. 轨迹留痕
10. SOS
11. 后台审核、风控、财务基础查询

### 2.2 一期上线标准

必须满足：

1. 顺路度规则生效
2. 接单频控生效
3. 平台线上支付可用
4. 轨迹留痕可查
5. 安全与审核后台可用

---

## 3. 环境规划

### 3.1 环境分层

建议至少准备 5 套环境：

1. 本地开发环境 `local`
2. 开发联调环境 `dev`
3. 测试环境 `test`
4. 预发布环境 `staging`
5. 生产环境 `prod`

### 3.2 各环境用途

#### local

用途：

1. 个人开发
2. 单元测试
3. 本地调试

#### dev

用途：

1. 日常前后端联调
2. Mock 接口替换真实接口
3. 功能自测

#### test

用途：

1. QA 测试
2. 回归测试
3. 提测验收

#### staging

用途：

1. 上线前演练
2. 预发布验证
3. 灰度验证

#### prod

用途：

1. 正式用户访问
2. 真实支付、真实数据

## 5. 代码仓库与目录建议

### 5.1 仓库形态建议

建议使用单仓多应用结构：

```text
sfc/
  apps/
    miniapp/
    admin-web/
  server/
  docs/
  scripts/
  deploy/
```

### 5.2 分支策略

建议使用简化 Git Flow：

1. `main`：生产分支
2. `develop`：开发集成分支
3. `feature/*`：功能分支
4. `release/*`：预发布分支
5. `hotfix/*`：生产修复分支

### 5.3 提交要求

每次提交应满足：

1. 单一主题
2. 说明清晰
3. 带对应任务号
4. 通过基本检查

提交信息建议：

```text
feat(order): 完成乘客确认上车接口
fix(payment): 修复支付回调幂等问题
docs(deploy): 补充 staging 发布步骤
```

## 6. 开发流程

## 6.1 需求冻结流程

开发前必须先冻结以下内容：

1. P0 页面清单
2. P0 接口清单
3. 订单状态机
4. 顺路度规则
5. 频控规则
6. 支付与退款规则

### 输出物

1. 前端开发文档
2. 后端开发文档
3. 接口清单
4. 数据表草案
5. 测试用例清单

## 6.2 开发启动流程

推荐顺序：

1. 初始化仓库与脚手架
2. 建立基础环境
3. 搭建认证、配置、日志、错误码
4. 建立前端壳、后端壳、数据库迁移能力
5. 开始主链路开发

## 6.3 开发协作流程

前端：

1. 先建页面壳
2. 再接 Mock
3. 最后接真实接口

后端：

1. 先出接口契约
2. 再出最小可跑接口
3. 最后补审计与异常处理

测试：

1. 先产出核心链路用例
2. 再跟进接口联调用例
3. 最后做回归矩阵

## 7. 本地开发环境搭建

## 7.1 通用依赖

本地建议安装：

1. Git
2. Node.js LTS
3. pnpm
4. Go 1.23+
5. Docker Desktop
6. 微信开发者工具
7. MySQL 客户端
8. Redis 客户端

## 7.2 本地服务建议

建议本地通过 Docker 启动：

1. MySQL
2. Redis
3. RabbitMQ 或 NATS
4. MinIO

### 示例

```bash
docker compose up -d mysql redis rabbitmq minio
```

## 7.3 小程序本地开发

步骤：

1. 安装依赖
2. 配置 `.env.local`
3. 在微信开发者工具中导入项目
4. 配置本地 API 域名或代理

## 7.4 后台本地开发

步骤：

1. 安装依赖
2. 启动 Vite
3. 配置本地代理

示例：

```bash
pnpm install
pnpm dev
```

## 7.5 后端本地开发

步骤：

1. 安装依赖
2. 配置本地环境变量
3. 执行数据库迁移
4. 启动 API 服务

示例：

```bash
go mod tidy
go run ./cmd/api
```

## 9. 数据库迁移流程

### 9.1 迁移原则

1. 表结构变更必须走 migration
2. 不允许手工改生产表结构
3. 每次发布前先评审 migration

### 9.2 迁移顺序

1. 用户与认证表
2. 车辆与司机表
3. 行程与匹配表
4. 订单与支付表
5. 钱包表
6. 安全与风控表
7. 后台运营表

### 9.3 发布前检查

1. 新索引是否影响性能
2. 默认值是否安全
3. 回滚脚本是否可执行

## 12. CI/CD 流程建议

## 12.1 CI 检查项

前端：

1. 依赖安装
2. ESLint
3. TypeScript 检查
4. 构建检查

后端：

1. `go vet`
2. 单元测试
3. 构建检查
4. migration 校验

## 12.2 CD 流程建议

### 开发环境

1. 合并到 `develop`
2. 自动发布到 `dev`

### 测试环境

1. 打 `release/*`
2. 自动发布到 `test`

### 预发布环境

1. release 分支打 tag
2. 发布到 `staging`
3. 执行预发布检查

### 生产环境

1. 从 `release/*` 合并到 `main`
2. 打生产 tag
3. 执行生产发布

## 13. 部署拓扑建议

### 13.1 生产拓扑

建议至少包含：

1. Nginx 反向代理
2. API 服务实例
3. MySQL 主从或高可用
4. Redis
5. MQ
6. 对象存储
7. 监控与日志系统

### 13.2 部署形态建议

建议优先：

1. 后端：Docker 容器化部署
2. 后台前端：Nginx 托管静态资源
3. 小程序：通过微信开发者平台上传发布

---

## 14. 前端部署流程

## 14.1 小程序部署

步骤：

1. 切换到目标环境配置
2. 执行构建与检查
3. 在微信开发者工具上传
4. 提交审核
5. 审核通过后发布

### 发布前检查

1. 合法域名已配置
2. API 环境指向正确
3. 支付参数指向正确商户
4. 地图 key 为正式 key

## 14.2 后台前端部署

步骤：

1. 执行构建
2. 上传构建产物到 Nginx 静态目录
3. 刷新缓存
4. 检查管理后台入口可访问

示例：

```bash
pnpm build
rsync -av dist/ deploy@server:/data/www/admin/
```

---

## 15. 后端部署流程

## 15.1 发布步骤

1. 拉取代码
2. 执行构建
3. 执行 migration
4. 发布新版本
5. 做健康检查
6. 验证关键链路

### 示例

```bash
go build -o bin/sfc-api ./cmd/api
./bin/migrate up
systemctl restart sfc-api
```

## 15.2 零停机建议

建议采用：

1. 蓝绿部署
2. 滚动部署
3. 容器多副本切流

## 17. 监控与告警

### 17.1 必须监控的指标

1. API 成功率
2. API P95/P99 耗时
3. MySQL 连接数
4. Redis 命中率
5. MQ 堆积
6. 支付回调失败数
7. 退款失败数
8. SOS 事件数
9. 导出任务失败数

### 17.2 必须告警的场景

1. 登录失败率异常
2. 支付回调连续失败
3. 订单状态流转异常
4. API 大面积 5xx
5. 数据库连接异常
6. MQ 积压严重
7. SOS 处理超时

---

## 18. 数据备份与回滚

## 18.1 备份要求

1. MySQL 每日全量备份
2. Binlog 保留
3. 对象存储重要文件生命周期管理
4. 配置文件单独备份

## 18.2 回滚策略

### 前端回滚

1. 后台前端回滚到上一版静态资源
2. 小程序回滚到上一个稳定版本

### 后端回滚

1. 发布前保留上一版二进制或镜像
2. 如 migration 不可逆，先做兼容式发布
3. 遇到支付问题优先关停相关入口，避免扩大资金问题

### 回滚原则

1. 先止血
2. 再回滚
3. 最后复盘

---

## 19. 应急响应流程

### 19.1 一级故障

定义：

1. 无法登录
2. 无法支付
3. 大面积下单失败
4. 后台不可用

处理：

1. 立即通知负责人
2. 回滚或切流
3. 排查日志
4. 发出故障说明

### 19.2 资金类故障

定义：

1. 重复扣款
2. 支付成功但订单未更新
3. 退款失败

处理：

1. 冻结相关流程入口
2. 导出受影响订单
3. 人工核对并补偿
4. 完成审计记录

## 21. 最终建议

本项目最怕的不是“功能做不完”，而是“开发顺序乱了”。正确顺序应该是：

1. 先冻结主链路和规则
2. 再搭好环境和脚手架
3. 然后完成前后端主链路开发
4. 再补合规后台和财务能力
5. 最后做上线演练、监控和回滚准备

只要按这个顺序推进，项目会更容易按一期目标稳定上线。
